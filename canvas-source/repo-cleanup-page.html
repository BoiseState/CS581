Repo Cleanup — Before You Start W2

I changed the student repo template. Your repo does not get those changes automatically, and there is a specific reason why. Five minutes of work, and the reason is worth understanding.

What changed

The template shipped workshops/week-02/threat-profile.md, a markdown file. The actual W2 deliverable is workshops/week-02/adversary-profile.json. Those are different artifacts in different formats. If you had opened your repo and filled in the file sitting there, you would have produced the wrong thing through no fault of your own.

The same mismatch existed for W3 through W9. Those weeks now carry a README.md naming the correct deliverables instead of a mis-named placeholder file.

Why you cannot just pull the fix

This is the part worth reading.

When you set up your repos, you copied the template files into a fresh git init. You did not fork or clone the course repo. That means your repository and the course repository share no common ancestor commit. Git has no way to reason about what changed between them, because as far as Git is concerned they are two unrelated projects that happen to contain similar files.

You can verify this yourself:

git log --reverse --format="%h %ad %s" --date=short | head -1

That is your repo's root commit. It will not match the course repo's root commit, and no git pull or git merge can bridge that gap cleanly.

You could force it:

git remote add upstream https://github.com/BoiseState/CS581.git
git fetch upstream
git merge upstream/main --allow-unrelated-histories

Do not do this. That --allow-unrelated-histories flag is Git telling you the operation does not make sense. It would succeed, and it would dump the entire course repository into yours: the syllabus source, the full curriculum file, the workflow guides, the example student work, everything. The template files would land under student-repo-template/primary-repo/ rather than at the paths your repo uses, so you would end up with two copies of everything at different paths and a large mess to clean up.

What to actually do

Two commands. From your primary repo:

git rm workshops/week-02/threat-profile.md
git commit -m "Remove retired W2 template file"
git push

If you already wrote notes in that file and want to keep them, move the content somewhere first. It is not a graded artifact, so your session log or a scratch file is fine.

If git rm says the file is not tracked, it was never committed. Delete it normally and move on.

Getting the new scaffolding, if you want it

Optional. The assignment and the W2 guide both contain the full schema, so you can simply create the files yourself. If you would rather start from the template versions, download the individual files rather than merging anything:

mkdir -p workshops/week-02/threat-cards

curl -o workshops/week-02/adversary-profile.json \
  https://raw.githubusercontent.com/BoiseState/CS581/main/student-repo-template/primary-repo/workshops/week-02/adversary-profile.json

curl -o workshops/week-02/threat-cards/cards.json \
  https://raw.githubusercontent.com/BoiseState/CS581/main/student-repo-template/primary-repo/workshops/week-02/threat-cards/cards.json

Both files contain a _comment key explaining what they are. Delete that key before you commit, and remember both files must parse as valid JSON when you are done.

This is the honest answer to "how do I get one file from another repository." Not a merge. You fetch the file you want.

Confirm you are clean

ls workshops/week-02/
git status

You should see no threat-profile.md, and a clean working tree once you have committed and pushed.

The actual lesson

This situation is common in real work, and it is a design problem rather than a Git problem.

Copying files out of a template gives you a clean history and full control, and it permanently severs you from upstream fixes. Forking keeps the upstream relationship and lets you pull changes, at the cost of carrying the upstream's history and structure. Neither is wrong. What is wrong is choosing one without knowing you chose it, and then discovering the consequence when the upstream changes.

We chose copy. I then changed the upstream. That is on me, and the cost is one git rm, which is about the cheapest possible version of this lesson. It is worth remembering the next time you set up a repository from someone else's scaffolding and have to decide whether you will ever want their updates.
